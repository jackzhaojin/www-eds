## Native indexing lifecycle

EDS maintains JSON query indexes of published documents. The configuration defines which
documents participate and which fields are extracted from their initial HTML or metadata.
Publishing creates or updates a document's row; unpublishing removes it. Changing the
extraction configuration needs a reindex of existing documents. Preview-only documents are
not new entries, and preview and live hosts expose the same set of published documents.

Our existing definition is `hlx-config/query.yaml`, applied through the configuration service
as `/content/query.yaml`. Do not add the retired repository-root `helix-query.yaml` even where
Adobe examples still use it. The current `/query-index.json` has one row per published page,
including one row for `/talks/`, not one row per talk embedded inside its row-list block.

## Content models to choose between

| Model | Source | How the JSON stays current |
|---|---|---|
| Writing | Existing article documents | Publish an article; EDS updates its index row. The listing filters/sorts the query index. |
| Talks, one document per talk | A normal or structured record document for each talk | Publish a record; EDS updates a dedicated talks index. A record need not be a full write-up. |
| Talks, one collection document | A structured-content document with an array of talk records | Publish the collection; its native JSON delivery endpoint returns the updated array. No query index is needed to assemble that collection. |

An ordinary index produces one row per document; it does not automatically turn nine rows in
the existing hub into nine records. Structured content supports schema-based forms and JSON
delivery. Multiple record documents can also be aggregated by a configured query index.

The editorial source must remain in git per `content/README.md`, with DA serving as the
publication source. The chosen model needs a documented authoring and sync process. Native
index updates remove the need for a custom code-bus JSON snapshot exporter.

## Dedicated index recommendation

Adobe's FAQ recommends dedicated indexes for common queries when needed; a separate index
per content type is not mandatory. One shared index is a reasonable small-site option when
all consumers need the same fields. For this collection, a dedicated `talks` definition is
useful because session date, event, talk kind, recording/material links, and stable hub
anchors have a different shape from the default page metadata. This is a data-contract
decision; the number of indexes does not itself improve SEO.

If we choose one document per talk, add that definition alongside `default`, with a distinct
JSON target such as `/talks-index.json`. Preserve the default index and the sitemap's current
source. No additional database or Worker is needed: both definitions use the EDS indexer.
A separate index does not create the talk documents or automatically split the current hub.

index; the merged configuration was applied and verified through GET/SET/GET. The request,
result and review boundary are in [the Admin API execution record](admin/EXECUTION.md).

## SEO and rendering

The query index supplies data; it does not automatically prerender the listing or generate
its JSON-LD. A browser-rendered listing can use real links and matching JSON-LD that Google
can process after executing JavaScript. Delivering the complete initial HTML remains useful
for crawlers that do not execute JavaScript.

Adobe's JSON2HTML service, marked AEM Sites Labs / early access, can convert a JSON endpoint
with a Mustache template into BYOM HTML during content ingestion. Preview/publish makes the
result a normal EDS page. API or index changes do not themselves define when the hub gets
repreviewed and republished; that refresh trigger still needs to be specified.

EDS content and site configuration are shared across code branches. A worktree isolates
code, not an overlay experiment. Site/Experience Workspace configuration and Cloudflare
changes remain Jack's stop points in AGENTS.md.

**Since Claude's review (2026-10-26)** the rows and the whole JSON-LD graph are generated:
by the edge Worker on www, in the served HTML, and by the browser on preview hosts. The hub
documents carry no rows and no `json-ld`. See
[the writing index record](../2026-10-26-writing-index/README.md#edge-rendering-and-generated-json-ld-claudes-review-2026-10-26).
